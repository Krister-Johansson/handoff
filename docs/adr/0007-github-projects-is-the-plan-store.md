# 7. GitHub Projects is the plan store

Date: 2026-10-02. Status: accepted. ADR 0008 changes one point: the worker reads the Project when the scheduler checks a project. [`docs/plans/organizations.md`](../plans/organizations.md) (issue #575) extends it to repositories owned by an organization: the Project, Priority, the token and webhooks below say how. Issue #602 adds the repository's milestones, read from and written to GitHub issues.

## Decision

handoff keeps no plan data. A project's plan of epics, stories and tasks lives on GitHub, and handoff reads it from there and writes status back as runs progress. `projects.plan_project_number` is the one column that points at the plan: the number of the GitHub Project that belongs to the handoff project. The plan mode and pins are handoff data about the plan, not part of it (see below).

- Hierarchy is GitHub's sub-issue relation in the project's repository: a story is a sub-issue of its epic and a task a sub-issue of its story. The labels `epic`, `story` and `task` mark the kind, because issue types exist only for organizations. An issue type is used when the label is missing, and depth after that. handoff sets no issue type, also in an organization. A label wins over a type, so an organization's types (Task, Bug and Feature by default) do not fight the labels: an issue typed Task without a kind label is a task, and Bug or Feature leave the kind to the depth.
- Status is the built-in Status field of a GitHub Project (v2), with the options Shaping, Ready, Running, In review and Done. A closed issue counts as Done whatever its Status says.
- The Project belongs to the repository's owner, a user or an organization. Every read of the Project goes through `repositoryOwner(login:)` with a `ProjectV2Owner` fragment, which answers for either owner type in one request and gives the type as `__typename`. Callers pass the repository owner's login, and handoff stores no owner type, since the type comes with every read and changes when GitHub moves the repository. Writes name node ids, and a task's item is matched by Project number and owner id, so they are the same for both owner types. `setup_plan` creates the Project under the repository's owner, and in an organization it refuses before creating anything when GitHub says the account cannot create Projects there. `list_github_projects` lists the owner's Projects the token can write. After GitHub moves a repository to another owner, `handoff project move` or Settings, Projects, Repository moved points the project at the new name and unlinks the old owner's Project, and `setup_plan` with `copy_from` copies the items into the new owner's Project. Priority is not copied.
- Priority decides the scheduler's priority order and is one of Optimize's ranks. handoff reads it and never writes it. The Project's own single select field named Priority wins, for both owner types, and an item without a value in it has no Priority; the organization's issue field does not stand in. Otherwise, when the repository's owner is an organization with a single select issue field named Priority, each issue's value comes from `issueFieldValues` on the issue, and the options rank by the field's `priority` number. Otherwise there is no Priority, and `start_scheduler` refuses priority order with a sentence that names both fields in an organization. A Project field that shows the organization's issue field as a column has `isIssueField` true and counts as the issue field, not as the Project's own. In the organization check on PR 585, GitHub refused a Project's own field named Priority next to that column ("Name has already been taken"), so one Project cannot hold both. The scheduler card, Project settings and `get_scheduler` say which field orders the tasks.
- Size and Estimate are fields on the same Project, next to Status and the date fields Start and Target. Size is a single select with the options S, M and L; another option reads as no size. Estimate is a Number field that holds a task's manual estimate in hours; 0 or less reads as no estimate. handoff reads them by name with the items, and a Project without them reads as having no size or estimate. `setup_plan` creates the fields the plan mode uses: Size in a Flow project, and Size, Estimate, Start and Target in a Timeline project. The dashboard's "Add the fields" does the same in Settings, Projects, and creates Size and Estimate from the timeline's banner. Both add S, M and L to an existing Size field and keep its other options.
- Milestones are GitHub's milestones of the project's repository, read from and written to GitHub issues (issue #602). handoff reads the repository's milestones, open and closed, once per plan read with GraphQL `Repository.milestones`, and each plan issue's own milestone with the Project's items. It sets or clears an issue's milestone with `updateIssue` and `milestoneId`, and `createIssue` takes `milestoneId` when a create tool names a milestone. Nothing about milestones is stored in Postgres: not the milestones, not an item's milestone and not the inheritance. A task without a milestone of its own inherits its story's, else its epic's, and a story its epic's; handoff computes that, and each milestone's progress over its tasks, on every read. Setting an existing issue's milestone goes through the GitHub port, so with a GitHub App it uses the installation token, as assignees do. handoff does not create, edit or close milestones: the approved design on #602 keeps that on GitHub, and GitHub offers it through REST only, with no GraphQL mutation. It sets no milestone on pull requests, and the Projects v2 Milestone field is not written, since GitHub takes its value from the issue.
- The capacity and a run's size are handoff configuration and run data, not plan data. `projects.plan_hours_per_day` is the person's hours of work a day, set in Project settings. It is configuration, so it sits next to `plan_project_number`. `runs.size` is the Size a run's task had when the run started, so a forecast keeps its runs when the task's Size changes later. Forecasts per size are computed from the runs on every read and never stored.
- The order of the work lives in Project order, the position of each item in the GitHub Project, which the scheduler reads. handoff writes Project order in a Flow project with `updateProjectV2ItemPosition`. It reads the items once, refuses when the queue on GitHub differs from the one the person or agent saw, keeps the longest run of items already in order, and moves each other item right after the item before it in the new order. The moves go at most 20 to a request, in order. Epics, stories, closed items, drafts and other repositories' items keep their places.
- The plan mode and pins are handoff data, not plan data. `projects.plan_mode` is `flow` or `timeline` and only a person changes it, in Project settings. Switching writes nothing to GitHub: Start, Target and Estimate stay on the items unread in Flow mode, and Project order stays as it is. A pin keeps a task at its place number in the order, and GitHub Projects has no field for it, so handoff stores pins in `plan_pins`, one row per project and issue with who pinned it, why (`drop`, `keep_here` or `set_order`) and when. `startRun` deletes a task's pins in the transaction that inserts its run. A pin on a task that is closed or out of the plan is ignored on read and deleted by the next order write.
- Access needs `GITHUB_TOKEN` as a classic token with the `project` scope, which reaches the Projects of users and organizations. A fine-grained token cannot reach a Project owned by a user account, and a GitHub App cannot either, since GitHub offers a Projects permission only for organizations. handoff reads every Project, a user's or an organization's, with the one classic token, and does not use the App for Projects. Without such a token there is no Projects port: the Plan page and the shaping tools say what is missing, and runs record `plan.skipped`. handoff checks the token's scopes from `X-OAuth-Scopes` and does not check `read:org`; the organization check on PR 585 used a token that also had `read:org`, so a token without it has not been tried on an organization's Project. An organization can still refuse the token: under SAML single sign-on when the token is not authorized for it, and when the organization refuses classic tokens. Those refusals show only when handoff reads that organization's Project. The port turns them, and a missing scope, into a `ProjectsAccessError` with a reason (`scope`, `sso` or `classic-blocked`) and a sentence that says what to do. The Plan page, `setup_project`'s plan check, `start_scheduler` and the shaping tools show the sentence, and a run records it as the `plan.skipped` reason.
- Sync is reads on demand. The Plan page reads the Project on every render and refreshes every 30 seconds while the browser tab is visible. The worker never polls the Project; it reads one issue's item when it writes a status. GitHub sends no webhook for changes to a user-owned Project. For an organization's Project GitHub has `projects_v2_item` webhooks, but only through an organization webhook or a GitHub App. handoff's repository webhooks and `pnpm dev:webhooks owner/repo` do not receive them, and handoff does not use them, so a Project of either owner syncs the same way. The `issues`, `sub_issues` and `issue_dependencies` deliveries are stored like any other and wake nothing; the Plan page shows the latest one as its last GitHub activity.
- Writes happen at run transitions (Running on start, In review when the pull request opens, Done after the merge, and on cancel the Status each task had before the run moved it), through shaping tools that show an approval card, and through a person's own actions on the Plan page: dates saved in the Schedule dialog, a size or estimate picked in the size popover, a bar dropped on the timeline, and Arrange's Save. In a Flow project the page writes Project order instead of dates: a dropped card, a choice in the rule-break dialog and Optimize's Apply. Those page writes go to GitHub at once, and a dropped bar or card offers Undo instead of an approval card. An order write saves its pin changes only after GitHub takes the order, so a refused write changes no pin. A run-driven write that moves a task onto the run's Status records the Status it had in the `plan.status` event's `from`, and cancelling the run writes that Status back to each task no newer run links. A task the run started on goes back to Ready, the gate every start passes. A run-driven write that fails becomes a `plan.skipped` event and never fails the run. A merge that closes the last open sub-issue of a story closes the story and writes Done on it, then does the same for the epic when that story or a task directly under it was the epic's last open sub-issue (issue #598). That write records the Status the parent had in `from`, a cancel never writes it back, and an issue closed by hand closes no parent. GitHub wins on conflict: handoff displays what it reads and overwrites Status only at those transitions.

## Consequences

- No cache tables and no copy of issues, statuses or hierarchy in Postgres. A change made on GitHub shows on the Plan page within 30 seconds, and nothing in handoff can drift from GitHub.
- The dashboard and the worker share the token's GitHub rate limit of 5,000 GraphQL points per hour with issue listing, pull request checks and the assistant. One read of a page of up to 100 Project items costs five points, Size, Estimate and Priority included (reading the issues' Priority issue field added one point on the pages measured on PR 582), and an open Plan page reads twice a minute. A drop on the timeline costs one read of the issue's item and one request that writes its fields.
- Reading milestones adds no points to a plan read. Measured read-only on PR 604 with `rateLimit { cost }`, the plan items query cost 5 points with and without each issue's milestone, on a user Project of 62 items and an organization Project of 4. The read of the repository's milestones costs 1 point a page of 100 (measured on a repository without milestones). No issue in the measured Projects had a milestone, and GitHub computes the cost from the query, not from the data. Setting a milestone costs one query for the issue's and the milestone's ids and one `updateIssue`.
- A drop in the Flow costs one read of the Project's items, one read of the Project node and one request with its moves. Optimize and `set_order` send one request per 20 moves. The item id that order writes need adds no points to the read.
- A person can move cards on GitHub's own board. A board move never starts, cancels or merges anything; the next run transition writes Status again.
- A repository owned by an organization gets the same plan on a Project the organization owns. Issue types do not replace the kind labels, Priority can come from the organization's issue field when the Project has no Priority field of its own, and the organization's Projects webhooks stay unused. The GitHub App path to Projects and fine-grained tokens remain open (`docs/plans/organizations.md`, open questions 4 and 5).
