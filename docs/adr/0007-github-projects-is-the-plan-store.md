# 7. GitHub Projects is the plan store

Date: 2026-10-02. Status: accepted. ADR 0008 changes one point: the worker reads the Project when the scheduler checks a project.

## Decision

handoff keeps no plan data. A project's plan of epics, stories and tasks lives on GitHub, and handoff reads it from there and writes status back as runs progress. `projects.plan_project_number` is the one column that points at the plan: the number of the GitHub Project that belongs to the handoff project. The plan mode and pins are handoff data about the plan, not part of it (see below).

- Hierarchy is GitHub's sub-issue relation in the project's repository: a story is a sub-issue of its epic and a task a sub-issue of its story. The labels `epic`, `story` and `task` mark the kind, because issue types exist only for organizations. An issue type is used when the label is missing, and depth after that.
- Status is the built-in Status field of a user-owned GitHub Project (v2), with the options Shaping, Ready, Running, In review and Done. A closed issue counts as Done whatever its Status says.
- Size and Estimate are fields on the same Project, next to Status and the date fields Start and Target. Size is a single select with the options S, M and L; another option reads as no size. Estimate is a Number field that holds a task's manual estimate in hours; 0 or less reads as no estimate. handoff reads them by name with the items, and a Project without them reads as having no size or estimate. `setup_plan` creates the fields the plan mode uses: Size in a Flow project, and Size, Estimate, Start and Target in a Timeline project. The dashboard's "Add the fields" does the same in Settings, Projects, and creates Size and Estimate from the timeline's banner. Both add S, M and L to an existing Size field and keep its other options.
- The capacity and a run's size are handoff configuration and run data, not plan data. `projects.plan_hours_per_day` is the person's hours of work a day, set in Project settings. It is configuration, so it sits next to `plan_project_number`. `runs.size` is the Size a run's task had when the run started, so a forecast keeps its runs when the task's Size changes later. Forecasts per size are computed from the runs on every read and never stored.
- The order of the work lives in Project order, the position of each item in the GitHub Project, which the scheduler reads. handoff writes Project order in a Flow project with `updateProjectV2ItemPosition`. It reads the items once, refuses when the queue on GitHub differs from the one the person or agent saw, keeps the longest run of items already in order, and moves each other item right after the item before it in the new order. The moves go at most 20 to a request, in order. Epics, stories, closed items, drafts and other repositories' items keep their places.
- The plan mode and pins are handoff data, not plan data. `projects.plan_mode` is `flow` or `timeline` and only a person changes it, in Project settings. Switching writes nothing to GitHub: Start, Target and Estimate stay on the items unread in Flow mode, and Project order stays as it is. A pin keeps a task at its place number in the order, and GitHub Projects has no field for it, so handoff stores pins in `plan_pins`, one row per project and issue with who pinned it, why (`drop`, `keep_here` or `set_order`) and when. `startRun` deletes a task's pins in the transaction that inserts its run. A pin on a task that is closed or out of the plan is ignored on read and deleted by the next order write.
- Access needs `GITHUB_TOKEN` as a classic token with the `project` scope. A fine-grained token cannot reach a Project owned by a user account, and a GitHub App cannot either, since GitHub offers a Projects permission only for organizations. Without such a token there is no Projects port: the Plan page and the shaping tools say what is missing, and runs record `plan.skipped`.
- Sync is reads on demand. The Plan page reads the Project on every render and refreshes every 30 seconds while the browser tab is visible. The worker never polls the Project; it reads one issue's item when it writes a status. GitHub sends no webhook for changes to a user-owned Project. The `issues`, `sub_issues` and `issue_dependencies` deliveries are stored like any other and wake nothing; the Plan page shows the latest one as its last GitHub activity.
- Writes happen at run transitions (Running on start, In review when the pull request opens, Done after the merge, and on cancel the Status each task had before the run moved it), through shaping tools that show an approval card, and through a person's own actions on the Plan page: dates saved in the Schedule dialog, a size or estimate picked in the size popover, a bar dropped on the timeline, and Arrange's Save. In a Flow project the page writes Project order instead of dates: a dropped card, a choice in the rule-break dialog and Optimize's Apply. Those page writes go to GitHub at once, and a dropped bar or card offers Undo instead of an approval card. An order write saves its pin changes only after GitHub takes the order, so a refused write changes no pin. A run-driven write that moves a task onto the run's Status records the Status it had in the `plan.status` event's `from`, and cancelling the run writes that Status back to each task no newer run links. A task the run started on goes back to Ready, the gate every start passes. A run-driven write that fails becomes a `plan.skipped` event and never fails the run. GitHub wins on conflict: handoff displays what it reads and overwrites Status only at those transitions.

## Consequences

- No cache tables and no copy of issues, statuses or hierarchy in Postgres. A change made on GitHub shows on the Plan page within 30 seconds, and nothing in handoff can drift from GitHub.
- The dashboard and the worker share the token's GitHub rate limit of 5,000 GraphQL points per hour with issue listing, pull request checks and the assistant. One read of a page of up to 100 Project items costs four points, Size and Estimate included, and an open Plan page reads twice a minute. A drop on the timeline costs one read of the issue's item and one request that writes its fields.
- A drop in the Flow costs one read of the Project's items, one read of the Project node and one request with its moves. Optimize and `set_order` send one request per 20 moves. The item id that order writes need adds no points to the read: a page of items costs four points with it and without it.
- A person can move cards on GitHub's own board. A board move never starts, cancels or merges anything; the next run transition writes Status again.
- A repository owned by an organization is the upgrade path: issue types become the kind marker, the Project can be organization-owned, and GitHub sends webhooks for organization Projects.
