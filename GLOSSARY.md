# Glossary

Terms used in handoff. Test names, types and issue titles use these words.

- **Project**: a connected GitHub repository plus its graphs and runs.
- **Graph**: the program. A versioned set of nodes and edges stored in graphology's export format. Edited in React Flow.
- **Node**: one unit of work with a single responsibility. Has a type from the catalog, a context selector, a contract and an executor.
- **Edge**: routing between nodes. Carries a condition evaluated against run state. A loop edge points back to an earlier node and has a max-attempts guard.
- **Run**: one execution of a graph against a task. Owns the run state document.
- **Run state**: the JSON document that accumulates as a run moves along edges: task, plan, diff summary, test results, PR number, feedback, attempt counters.
- **Node execution**: one attempt of one node inside a run. Status is pending, running, waiting, passed, failed or repaired.
- **Context packet**: the subset of run state and repo files a node execution may read. What the node is allowed to believe.
- **Contract**: the schema a node execution's output must satisfy plus the deterministic checks the engine runs before following any edge. What the node must deliver.
- **Deterministic check**: a true or false test run by the engine, never by a model: tests pass, diff within owned paths, PR exists.
- **Waiting**: a node execution that has yielded and will be resumed by an external event, such as a GitHub webhook or a human answer.
- **Human gate**: a node that waits for a person to answer a question or approve a step in the dashboard.
- **Exhausted gate**: the Human gate a loop edge's `onExhausted`, or the graph's `exhaustedGate`, names for when the loop runs out. Any Human gate can be one. It asks retry, continue or abort whatever its ports are, and the engine routes the answer from the step that wanted another round; abort cancels the run.
- **Question**: what a human gate, or a paths question, asks a person, stored with its options and what the gate shows for review. It is open until someone answers it, and the inbox lists the open ones.
- **Notification**: something a person is told: a tone, a title, a body and an optional link, written by whoever sends it and shown as it is. Read or unread, never done. A question has a notification, and the two are separate rows.
- **Coder node**: a node whose executor spawns the Claude Code CLI in a worktree.
- **PR node**: a node that opens or updates a pull request, then waits for checks and reviews and routes the feedback.
- **Paths question**: what a node execution asks when the diff-within-owned-paths check is its only failing check. It waits, names the files outside the plan, and a person answers Allow for this run, Send back or Fail the step.
- **Review item**: a finding an external reviewer left on a run's pull request, which a PR node with `reviewThreads.reply` on sends to the coder: an unresolved inline thread, a review summary that is not an approval, or a walkthrough note or failed or warning pre-merge check in CodeRabbit's summary comment. It has a handle that stays the same for the run (`R1`, `R2`), the coder's verdict and evidence, handoff's answer on GitHub, and a state: open, answered, awaiting_review, resolved, disputed, reraised, left or gone. Items are rows in `review_items`, and the PR node is their only writer.
- **Answer-only round**: a round in which the coder only declined, asked about, marked as duplicate or settled its review items, with HEAD still at the commit the PR node pushed and a clean worktree. The engine sets `answerOnly` on the coder's output, and the run goes straight back to the PR node without the tester, code review, gates or demo, and without counting another loop.
- **Re-review**: the PR node's wait, after it answered a thread item on GitHub, for that reviewer's next review. A review submitted after the answer that opens no thread on the same lines lets handoff resolve the thread. It never resolves a thread in the step that answered it. A step in this wait reports `waiting_on: re_review`, up to the reviewer's limit (30 minutes for a bot, 24 hours for a person).
- **Disputed item**: a review item handoff cannot settle. The coder declined it again, or still found it unclear, after the reviewer's reply; the reviewer did not review again within its limit; or the next summary still lists a summary item the coder fixed twice. The PR step asks one question about its disputed items, and a person chooses Resolve, Send back or Leave for each.
- **Worktree**: a git worktree created per run where a Coder node works. A failed run keeps it until the run is repaired or cancelled, or `handoff gc` removes it.
- **App launch**: how handoff starts a run's app for Demo and Try it steps, as one configuration of `.claude/launch.json`. The repository's file wins; without it, the project's App launch setting in Project settings, stored in `projects.launch`, applies. Environment values in the setting are plain text and never secrets. In Docker workspace mode the app runs in its own container next to the run's, from the same image, with its port published on the loopback addresses only.
- **Test start**: the App launch section's check that the app starts. It runs the setup command, the services, the seed command and the app from a fresh worktree of the default branch, outside any run, with the form's values whether saved or not. It stops when a person stops it, when another Test start of the project begins, or after 10 minutes, and removes its worktree.
- **Library**: the catalog of skills and MCP servers that can be enabled per node or per edge.
- **Engine**: the worker process that schedules node executions, evaluates contracts and edges, and writes events.
- **Scheduler**: a project's switch that lets handoff start runs on its own. Once a person turns it on, the worker starts runs on the plan's Ready tasks, up to a limit of active runs, and starts nothing while a failed run or a pending permission request holds the project. It is not the engine's scheduling of node executions, which the engine does for every run.
- **Size**: how big a task is, S, M or L, in the single select field Size on the plan's GitHub Project. A person sets it on the dashboard, over MCP or on GitHub. The planner proposes a size in its plan, and the dashboard shows a proposal dashed until a person picks a size; only a person's pick reaches GitHub. A Size option other than S, M or L reads as no size. A run records the size its task had when the run started, so a later change does not move old runs between sizes. Epics and stories have no size; they show the sum of their tasks.
- **Estimate**: a task's manual duration in hours, in the Number field Estimate on the plan's GitHub Project. A person types hours or days ("3h", "2d"), and a day is the project's capacity. An estimate overrides the forecast of the task's size. An Estimate of 0 or less reads as no estimate. Only a Timeline project uses estimates; a Flow project refuses one.
- **Forecast**: what a size usually takes in this project: the median wall time of the project's succeeded runs of that size that link exactly one task, split into agent, queue and waiting-on-you time, with the median reported cost and the number of runs. A size with fewer than 5 runs uses its default (S 30m, M 1h, L 2h). handoff computes forecasts from the runs when it reads them and stores none. A run without a recorded size counts under its planner's proposal, else under its task's current Size. A task's duration is its estimate, else the forecast of its Size, else the forecast of its planner's proposal.
- **Capacity**: the person's hours of work a day on a Timeline project's plan, 1 to 24, 6 unless changed. A sized task's bar on the timeline is its duration over the capacity, in days, and Arrange fills each day up to it. Every day counts, weekends too. Runs that work at the same time add no capacity.
- **Plan mode**: how a project plans its work, Flow or Timeline, in `projects.plan_mode`. Only a person changes it, in Project settings under Plan, Plan mode. A project that existed before plan modes plans in Timeline mode, and a project added since starts in Flow mode. The Plan page's third view, the MCP tools, the server instructions and the `handoff` skill follow the mode, and a tool that belongs to the other mode refuses with a sentence that names what to use instead. Switching writes nothing to GitHub: Start, Target and Estimate stay on the items, and Project order stays as it is. The scheduler works the same in both modes.
- **Timeline**: the plan mode with dates. Items have Start and Target, tasks have sizes and estimates, and the project has a capacity. The Plan page's third view is the timeline.
- **Flow**: the plan mode without dates or hours. The plan is an order of tasks and their blockers. The Plan page's third view, also called the Flow, keeps the timeline's tree on the left and puts each task's card on its row, in the lane the scheduler would start it in. It places the cards by simulating the scheduler from now. A card's length is its size's forecast and only decides which lane frees first; a task without a size counts as M. The Flow's queue is the Ready tasks the scheduler may start, in its order, followed by the Shaping tasks in Project order. "Next n" is a task's place in that queue, blocked tasks counted.
- **Project order**: the order of the items in the plan's GitHub Project. The scheduler starts Ready tasks in Project order unless it orders by Priority. In a Flow project handoff writes Project order: a drop, a choice in the rule-break dialog, Optimize's Apply and `set_order` move items with GitHub's `updateProjectV2ItemPosition`, and a split plan's new parts land right after the run's task. Epics, stories, closed items, drafts and other repositories' items keep their places.
- **Priority**: how urgent a task is, read from GitHub and never written by handoff. It has two sources. The Project's own single select field named Priority comes first, for a user's and an organization's Project alike, and its first option ranks highest. When the Project has no such field and the repository's owner is an organization with a single select issue field named Priority, each issue's value in that issue field counts, and its options rank by their priority number (Urgent before High in GitHub's default field). A Priority column that shows the organization's issue field on the Project counts as the issue field. Without either there is no Priority. The scheduler starts tasks by Priority when its order is priority, Optimize ranks by it, and the scheduler card, Project settings and `get_scheduler` name the source.
- **Lane**: one run the scheduler may hold at once, drawn as a slot in the Flow. A Flow has `max_runs` lanes, or 1 for a project whose scheduler was never turned on. An active run keeps its lane whatever it waits for, because it counts toward `max_runs`. Runs started by hand beyond `max_runs` get lanes of their own that close when their runs end. The Claude cap does not change the number of lanes.
- **Pin**: a mark that keeps a task at its place number in a Flow project's order. handoff stores pins in its `plan_pins` table, keyed by project and issue, because GitHub Projects has no field for them. A person pins a task by dropping its card, which every choice of the rule-break dialog also does. An agent pins only through `set_order`'s `pin` list, when the person asks for a task's place to stay. Clicking the pin on the card or the Pinned tag in its row unpins it, and so does `set_order`'s `unpin`. Optimize and `arrange_plan` never pin or unpin. A pin ends when its task's run starts, and a pin on a task that is closed or out of the plan goes at the next order write.
- **Optimize**: arranges a Flow project's queue for the earliest finish on the scheduler's lanes, over the whole queue or over the epics, stories and tasks ticked in the tree. Pinned tasks and tasks outside the selection keep their places. Each other place, from the front, takes the highest-ranked task whose blockers in the queue sit earlier. The rank is the longest chain of work the task starts, then the work it unblocks, then Priority, then the larger size, then its current place. The Plan page shows a preview and writes nothing until Apply, and the toast's Undo writes the previous order back. `arrange_plan` gives agents the same preview.
- **Milestone**: a GitHub milestone of the project's repository, with a title, an optional due date and a state, open or closed. It gives a release or a phase a due date across epics. Milestones are created, edited and closed on GitHub; handoff reads them with the plan, sets an issue's milestone on GitHub and stores nothing about them. A task belongs to its own milestone, else its story's, else its epic's, and a story without one belongs to its epic's. A milestone's progress counts its tasks only, own and inherited, with a closed task as done. In Timeline mode it ends on the latest Target of its tasks, which makes it late or early against the due date, and tasks without dates are named and not counted. In Flow mode it ends after its last task in the order, with no day and no late or early. The scheduler and Optimize do not order by milestone, and runs never set one.
- **Event**: one row in the events table, streamed to the dashboard. CLI stream-json lines become events.
